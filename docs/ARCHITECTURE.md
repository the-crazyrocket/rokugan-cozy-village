## Orchestrator amendments (these OVERRIDE anything below that disagrees)

The design below was written for maximum merge safety. For a one-player hobby game some of that governance costs more than it saves, so:

1. **No `OWNERSHIP.json`, `ALLOC.json`, `FACADE.json`, `IDS.json` allocation lints, `check-ownership.mjs` or `tests/budget.json`.** `docs/IDS.json` stays only as a list of shared item ids (S4). WPs still own files named `wpXY-*`, and the arch lint (`tests/logic/arch.mjs`: no system-to-system imports, [P]/[T] tiers, no `Math.random`/`Date.now` in P/T files, unique resolver priorities, unique slice names, every emitted event declared) stays. Priority and key collisions are caught by that lint after a merge and fixed by the orchestrator.
2. **No pre-created stubs (S12 shrinks).** Index files (`packs/index.js`, `systems/index.js`, `ui/sheets/index.js`, `render/views/index.js`, `style.css` imports) are GENERATED by `tools/gen-indexes.mjs`, which scans each directory for files named `wp*` (plus the fixed base files, in a stable order). A WP fork runs the generator to see its own files; `tools/fork.mjs` ignores generated files when merging and the orchestrator reruns the generator in the main tree. A WP creates its own files; it never edits another WP's.
3. **No `modulepreload` tags.** Keep the build stamp: `tools/stamp-build.mjs` writes `BUILD_ID` into `src/version.js`, `<meta name=build>` and `sw.js` (`CACHE = 'rcv-' + BUILD_ID`), and the load-safety rules of section 3.7 stay in full.
4. **Content schemas** (S4) must be real, but only for the domains Waves 1-3 use; keep them small and strict-by-default, extendable with `schema.extend`.
5. **Parallel work uses `tools/fork.mjs`** (separate copies merged file by file), never git worktrees. No git writes, no commits, unless the user asks.
6. **Art:** bridge repaint, new blockouts and sheets go through the Codex pipeline directly when a step needs them (venv python at the scratchpad path in the agent rules; `postprocess.py <names>` with explicit names).
7. Everything else (core APIs, systems and registries, scheduler and away, save slices and load safety, world arrays and `applyEdit`, goldens, logic layer) is built as written.

## TL;DR

1. **Game becomes a shell.** It owns a `Core` (bus, registries, scheduler, time, inventory, save). Every feature is a **System** with `init`, `update`, a save slice and registry entries. Systems never import each other. They talk by events and by `ctx.use()` for declared reads.
2. **Everything is content.** One appended `add('fish', id, {...})` block adds a fish. Fish, bugs, visitors, dialogue and crop niches share one JSON **conditions** engine.
3. **Merge safety by construction.** Wave 0 pre-creates a stub for every file a WP will need. Each WP owns files named `wpXY-*` plus a listed set. `docs/OWNERSHIP.json` and `tools/check-ownership.mjs` verify it. The only shared files are pre-listed index files that WPs never edit.
4. **Node logic layer.** Systems call `ctx.say/sfx/fx`, which emit events that nobody hears in Node. `tests/logic.mjs` runs content, events, scheduler, conditions, seasons, save migration and pacing in seconds.
5. **Safe refactor.** Code is moved verbatim first, then rewritten, one system at a time, with golden fixtures captured from the current working tree.
6. **Time and saves.** Real-calendar seasons. Projects, processing, traps, mail and visitors are persisted scheduler entries that catch up while away. Save v4 is per-system slices with a migration registry. The world slice stores full RLE arrays (not a generator diff).
7. **A save is never destroyed by a load failure.** "No save" and "save present but unreadable" are different states. The second shows a recovery card, copies the raw JSON to a quarantine key and refuses all writes (section 3.7). The dev clock never touches the real save (section 3.6).
8. **Wave 0 ships the cross-WP contracts**, not only the plumbing: real content schemas and shared item ids (`docs/IDS.json`), the tile-edit primitive (`world/edit.js`), the allocation table (`docs/ALLOC.json`), `ctx.hud` and the tool overflow, the day-roll contributor API, and registry leaf modules. A WP fork can therefore pass every gate alone.

## 1. Philosophy and what it optimises

In priority order:

1. **Parallel merge safety.** Exclusive files per WP; shared files are pre-listed registries; a lint enforces both.
2. **A fast node logic layer.** Logic never touches `ui`, `sound` or `particles`. The same engine drives `tools/simulate.mjs`.
3. **3-minute check-ins.** Anything that should happen while away is a persisted scheduler entry or a pure function of time. One "away" summary reports it. No energy, no punishment (`docs/DESIGN.md`): catch-up only adds.
4. **No regressions.** `Game` and `UI` keep their method names, `window.__game` is unchanged (except that `skip` exists only under `?dev`, section 3.6), and old paths stay as re-export shims until Wave 6.

Convention: **higher `priority` runs first; ascending `order` is display order.** Costs accepted: indirection and many small modules. `tests/budget.json` caps eager modules at 220; UI sheets load lazily (`import()` on first open); `tools/gen-preload.mjs` writes `modulepreload` tags into `index.html`.

Tiers: **[P]** pure (no `three`, no DOM; imports in Node). **[T]** imports `three` math or geometry, or imports a [T] module, but needs no DOM or WebGL. **[B]** browser only. Logic tests may import P and T. A module's tier is the highest tier of anything it imports, and `arch.mjs` checks this by walking imports (a [P] file that imports a [T] file fails). **Registry leaf modules** (`assets/blockouts/registry.js`, `assets/sheets/registry.js`, `core/sfxreg.js`) are [P] and import nothing, so packs can call `defineBlockout`, `defineSheet` and `defineSfx` without reaching a facade or the browser.

## 3. Core APIs

### 3.1 Event bus (`core/bus.js`, `core/events.js`)

```js
bus.on(name, fn(payload, meta), { priority = 50, owner }) -> off()   // higher first, then registration order
bus.once(name, fn); bus.onAny(fn); bus.emit(name, payload = {}) -> payload
// meta = { name, at: ctx.now(), away: bool, seq }
ctx.say(text, icon, tone)  ctx.sfx(name, opts)  ctx.fx.burst(x, y, z, opts)  ctx.invalidate('veg'|'crops'|'ground'|'terrain')
```

- Bands: `PRIO.STATE = 90` (inventory, stats, requests, collection), `PRIO.GAME = 50`, `PRIO.VIEW = 10` (toast, sfx, particles, ui refresh), so state settles before a toast.
- Emit is synchronous and error-isolated, with re-entrancy depth capped at 8. In `core.strict` (tests) an unknown event, a payload that breaks its schema, or a handler error throws.
- In catch-up `meta.away = true`. `ui/feedback.js` and sound ignore away events; `away.js` records them.
- Events are facts. Numeric tweaks go through `bus.apply('fish.window', value, payload)` filters.

| event | payload |
|---|---|
| `harvest` | `{crop, n, quality:1..3, x, z, via:'hand'\|'sweep'\|'sprinkler', giant?}` |
| `cropRipe` | `{crop, x, z}` (also emitted in catch-up) |
| `catch` | `{kind:'fish'\|'bug', id, size, water, spot:{x,z}, bait, first, via:'rod'\|'trap'\|'net'}` |
| `forage` | `{item, n, x, z, first}` |
| `place` | `{prop, id, x, z, rot, via:'build'\|'move'\|'project'\|'load'}` |
| `remove` | `{prop, id, x, z, to:'bag'\|'gone'}` |
| `craft` | `{recipe, bench, made:{id:n}, used:{id:n}}` |
| `cook` | `{dish, ingredients:[id], discovered, quality}` |
| `visit` | `{visitor, phase:'arrive'\|'leave'\|'photo', x, z, gifts:{id:n}}` |
| `gift` | `{to, item, reaction:'love'\|'like'\|'neutral'\|'dislike', hearts}` |
| `wake` | `{fortune}` |
| `projectDone` | `{project, doneAt, unlocks:[{type,id}]}` |
| `dayChange` | `{day, prev, skipped}` (`skipped` = days missed; daily rolls once) |
| `seasonChange` | `{season, prev, year}` |
| others | `itemGain/itemLoss {item,n,reason}`, `moneyChange {delta,reason}`, `sell/buy {item,n,total}`, `offer {fortune,offering,gave}`, `terraform {x,z,from,to,kind}`, `waterChange {rect}`, `mail {from,id}`, `trapReady {id}`, `saveFailed {reason}`, `projectWaiting {project, why}`, `say`, `sfx`, `fx`, `invalidate` |

WP-private events are declared in the owning system's `events:` field. A cross-WP event is one appended line in `core/events.js`.

### 3.2 Systems, ctx and registration points

```js
export default defineSystem({
  name: 'farming', needs: ['props'],                    // boot order + permission for ctx.use('props')
  events: {},                                           // private event schemas
  slice: { version: 1, order: 30, defaults(), serialize(ctx), load(d, ctx), migrate: { 1: (d, env) => d2 }, shift(d, dx, dz) },
  facade: { harvest: 'harvest', crop: 'crop' },         // Game method name -> api method (Wave 0 systems only)
  init(ctx), newGame(ctx), start(ctx, { fresh }),       // start runs after load, before the first frame
  update(ctx, dt, t),                                   // optional
  api(ctx) { return { crop, stage, timeToRipe, harvest }; },
});
```

`ctx` (the `Core`) holds `now()`, `mono()` (monotonic ms for animation timing such as the bite wait), `rng`, `bus`, `content`, `cond`, `time`, `sched`, `away`, `inv`, `money`, `flags`, `world`, `groundY(x,z)`, `use(name)`, `ext` (free namespace per WP), and the notifiers above. Registries (`core/hooks.js`); a WP adds a new registry with `ctx.hooks.define(name)` without touching core:

```js
ctx.tools.add('hoe', { use(t, ctx), mesh? })                         // replaces Game.useTool switch
ctx.hotbar.add({ id, order, compact, icon, name, hint, when: cond }) // replaces HOTBAR and ui SEEDS
ctx.resolvers.add({ id, priority, fn(t, ctx) -> action|null })       // replaces Game.resolve; highest priority non-null wins, else walk
ctx.actions.add(kind, { range, queueable, sweep, button, perform(a, ctx) }) // replaces ACTIONS, SWEEP_KINDS, ACTION_KINDS, perform switch
```

### 3.5 Scheduler and away (`core/sched.js`, `core/away.js`)

```js
sched.schedule(kind, at, data, { key, repeat:{every}|{rule:'day'}, catchUp:'collapse'|'each'|{max}, owner, xz }) -> id  // key replaces
sched.cancel(idOrKey)  sched.due(now)  sched.pending(kind?)  sched.next(kind?)  sched.serialize()/load(d)  // { seq, entries }
sched.handler(kind, (entry, ctx, { late, away, missed }) => void | { reschedule: atMs })
```

**Catch-up** (`core.catchUp(from, to)`, on `load`, `resume`, `skipTime`):
1. Merge due entries with synthetic, unpersisted boundaries (`@day` at each 05:00, `@season`, `@festival`) in `(from, to]`, ordered by `(at, seq)`.
2. While a handler runs, `ctx.now()` returns that entry's `at`: a trap that fired at 14:00 stamps its catch at 14:00 and chains from there. `meta.away = true`.
3. A handler may schedule entries that are due inside the window; they run in the same pass. **Caps apply to repeating entries and synthetic boundaries only:** 10,000 repeat firings and 366 simulated days, after which repeats and boundaries jump to `to` with no punishment. **One-shot entries (project completion, processing, trap, mail, visitor leave) are always fired,** whatever the window length, so a project finishing during a long absence is never dropped. Repeating entries default to `collapse` (one call with `missed:n`). Visitor rolls use `{max: 72}`.
3a. **Clock regressions.** `catchUp(from, to)` with `from > to` (a changed timezone, a manual clock change, `savedAt` in the future) is a no-op: nothing fires, nothing is lost, and `savedAt` is clamped to `to`, so the next real advance starts from there. DST and timezone changes only move `dayKey` and `hour`, never `now()`, and `dayChange` fires at most once per distinct `dayKey`.
4. The last `dayChange` carries `skipped`; Hana's daily roll runs once, with the same single `mulberry32` stream as today.

Farming stays timestamp-based (`tickCrops`). `farming.start` compares stages before and after catch-up and emits `cropRipe`. Entries that carry coordinates must put them in `xz` so `shift` can re-centre them.

**Away.** `away.begin(from)` collects `meta.away` events. Systems register `away.describe(event, items => ({icon, text, order}))`. `away.end()` returns `{awayMs, days, lines, reveals:[{kind,id}]}` plus the legacy `{ripe, grew, newDay, forage}`. It is stored in the `away` slice until acknowledged, so a reload mid-reveal loses nothing. `reveals` is the project-finished card queue shown by `ui/sheets/reveal.js` after the Today card. Threshold stays `AWAY_MS = 10 min` **for the Today card only**: `Game.load`/`resume` show a summary when `awayMs > AWAY_MS || newDay || reveals.length > 0`, so any non-empty `reveals` list bypasses the threshold and a project that finishes during a 5-minute check-in still gets its reveal card (opened straight to `reveal`, without Today when nothing else happened). **Foreground completion:** a `projectDone` that fires while the app is open (`meta.away = false`) pushes the same `{kind:'project', id}` onto the pending `reveals` and shows a non-blocking ribbon ("The pavilion is finished", tap to open the reveal card; it never interrupts a fishing cast or a build preview); acknowledging a reveal removes it from the `away` slice. `game.away` still mirrors the pending summary for `main.js`.

### 3.6 Time and season (`core/time.js`)

```js
time = createTime({ realNow, perf, carry, devOffset });  time.now(); time.mono(); time.skip(ms)   // now = real + carry + devOffset
time.dayKey(ms); time.hour(ms)                      // dayKey rolls at 05:00 local, as today
time.season(ms)  // month of the village day, UTC date math (DST-safe): Mar-May spring, Jun-Aug summer, Sep-Nov autumn, Dec-Feb winter
time.seasonInfo(ms) -> { season, year, dayOfSeason, daysInSeason, progress, next:{season, at} }
time.weather(ms) -> { kind:'clear' }               // placeholder; time.weatherProvider(dayKey, hour) swaps in Wave 4
time.festival(ms) -> id | null                     // from the festivals domain
time.override = { season, hour, weather }          // gallery and tests; while set, saving is disabled
time.savingAllowed -> bool                          // false when override is set, when `?date` was used, or in a read-only session (section 3.7)
```

A hemisphere setting (`core.time.hemisphere`, default `'north'`) shifts seasons by 6 months. `?date=YYYY-MM-DD` moves `devOffset`, so skipping 90 days really crosses seasons. `?season=autumn` sets `time.override`.

**The dev clock never reaches the real village.** Seasons follow the real calendar, so a persisted dev offset would permanently move a real village's seasons, schedule entries and crops.
- `devOffset` (from `?date`, the dev panel and `__game.skip`) is session-only: it is never written to the `core` slice. The only persisted time field is `core.time.carry`, which is the v3 `timeOffset` carried over unchanged by the v3 to v4 migration so every stored timestamp stays consistent (almost always 0); nothing ever changes `carry` afterwards, and `S10` logs a one-line note if `|carry| > 1 day`.
- `?dev` switches to the **dev namespace**: `save/dev` (and `dev-backup`, `dev-quarantine`) instead of `SAVE_KEY`. On first use it copies the real save once (`?dev=reset` recopies, `?dev=empty` starts blank), so dev sessions run on a throwaway copy and may save normally, including the skipped time inside that copy. Browser flows that skip time run with `?dev&nosw`.
- `?date`, `?season` and `time.override` set `time.savingAllowed = false` for the whole session: no write to any namespace, no backup.
- The real namespace refuses any write while `devOffset !== 0` or `time.override` is set.
- `__game.skip`, the dev panel and the `?date`/`?season` parameters exist only when `?dev` is present; without it `__game.skip` is `undefined`. A visible **DEV** badge (date, offset, "saving off" when relevant) is shown whenever any of them is active, and it cannot be dismissed. `tests/browser/harness.mjs` adds `?dev` itself. `Game.update` keeps its 0.5 s poll and calls `time.tick()` which emits `dayChange`/`seasonChange`. Today (2026-10-23) is autumn.

**Soft-lock rule.** No Fortune offering, project cost or recipe gate may need an item that is unobtainable in any one season. `tests/logic/seasons.mjs` computes each item's seasonal availability from `when`/`seasons` and fails otherwise.

### 3.7 Save slices (`core/save.js`)


|---|---|---|

**Load safety (S10; nothing here may be skipped).** `save.inspect()` replaces `hasSave()` as the entry point and returns one of four states, so "no save" and "a save I cannot read" can never be confused:

| state | meaning | `main.js` does |
|---|---|---|
| `none` | no main slot and no backup | `newGame()`, help card |
| `ok` | loaded and migrated | normal load |
| `unreadable` | a slot exists but JSON, migration or a slice `load` threw | **never `newGame()` and never `save()`**: copy the raw main-slot string (and the backup string) to `save/quarantine-<savedAtOrNow>` first, enter read-only, open the recovery card (`ui/sheets/recover.js`): try the backup slot, try the `pre-v4` copy, restore from an RCV2 code, export the raw JSON, or (only on an explicit second confirmation) start a new village in a fresh namespace without deleting the old keys |
| `future` | `env.v` or any slice's stored `v` is newer than this build knows | read-only; recovery card says "this village was saved by a newer version, reload to update" with a reload button |

- **Read-only mode** (`core.readOnly`) is a hard gate inside `save-storage.writeSave`: it throws in strict mode and returns `{ok:false, reason:'readonly'}` otherwise. `pagehide`, autosave, `newGame` and `skipTime` all go through it. The backup slot is written only from a state that loaded successfully and passed a re-parse of the serialized string.
- **A slice with a newer stored `v` is preserved byte for byte** (as an unknown slice), the world is not mutated, and the session is read-only. Unknown slices are re-written only in a writable session.
- **One failing slice does not discard the others, and does not allow a write**: the session is read-only, the failing slice's raw JSON is kept in the quarantine copy, and the recovery card offers "open without that part" only as an explicit read-only preview.
- **Mixed module graphs cannot write.** `src/version.js` `BUILD_ID` is compared at boot with `<meta name=build>` in `index.html` and with the service worker's `CACHE` (`rcv-<BUILD_ID>`). `tools/gen-preload.mjs` regenerates all three, and **the orchestrator runs it at the end of every wave and every S-step that changes modules**, not only in S13, so a stale cached module beside a new one is detected and the page shows an "update available, tap to reload" card, read-only until reloaded. The write-refusal rule above is the second line of defence.
- **Save failure is visible.** `writeSave` returns `{ok, reason}` (`'quota'|'denied'|'readonly'|'serialize'`) instead of `false`. A failure emits `saveFailed {reason}`; the HUD shows a persistent "Not saved" marker (`ctx.hud`, `corner`) with a tap that offers the RCV2 export, until the next successful write clears it. The `save` browser flow stubs `localStorage.setItem` to throw `QuotaExceededError` and asserts the marker.
- **Photos are not in the save.** 3.3 stores image blobs through `core/blobs.js` (IndexedDB in the browser, `memory` in Node) and the `scrapbook` slice keeps only `{id, blobId, at, meta}`. RCV2 codes and `pre-v4` copies exclude blobs and keep the metadata; the scrapbook sheet offers a separate "export photos" download. A missing blob renders a placeholder frame, never an error.

Also: v1 and v2 saves chain through the existing steps to v3 and on to v4. `SAVE_KEY` and the `RCV2` prefix are kept, and `game/save.js` keeps exporting `migrate, readSave, writeSave, hasSave, clearSave, encodeSave, decodeSave, SAVE_VERSION`. The raw v3 JSON is copied once to `rokugan-cozy-village/save/pre-v4` (rollback: copy it back to `SAVE_KEY`); the pre-v4 copy protects only that one transition, and the quarantine and write-refusal rules above protect every later one. Authored coordinates stay legacy; `save.shiftAll(env, dx, dz)` calls every slice's `shift`.

## 4. World data model (interface; Wave 1 implements)

`World({w, h})` with `i = z*w + x`. Wave 0 keeps 40x40.

| array | persisted | meaning |
|---|---|---|
| `kind` | yes | Uint8. Today's `T` values 0-4 keep their numbers; new: `GRAVEL 5, STEPPING 6, BOARDWALK 7, PLAZA 8`. `WATER` means no ground. |
| `height` | yes | Uint8 0-4. Land: surface level, `y = 0.5 * h`. Water: the water-surface level, `y = 0.5*h + WATER_Y` (so hill ponds work). |
| `water` | yes | 0 land, 1 sea, 2 pond, 3 stream, 4 tide pool. |
| `fresh` | derived | `water >= 2`; kept as an array for the ground shader. |
| `wet` | derived | 0 dry, 1 damp (beside water or sprinkler), 2 flooded; read by crop niches. Timed watering stays in `farming`. |
| `stairs` | derived | Direction (bits 0-2) and ramp bit, rebuilt from placed props that have `stairs:{dir}`. One source of truth: the prop. |
| `flow`, `fall` | derived | Stream direction and waterfall drop, computed by `world/water.js` via `world.registerDerived()`. |

The `world` slice stores `kind`, `height` and `water` as full RLE arrays plus `{w,h}` (about 4 KB at 64x64). It is independent of any generator, so changing `generate.js` cannot corrupt old saves. `legacy40.js` is used only once, at the v3 to v4 step.

**Replacing the old API.**

| old | new |

| `W`, `H` | `world.w`, `world.h` (converted per file by the file's S6B owner; `arch.mjs` bans `import {W,H}` after S9) |

`world.version` and a dirty-chunk set (16x16 tiles) drive the renderer.

**Tile edit contract (`world/edit.js`, written and tested in S9, orchestrator-owned).** Terraform (2.1), water digging (1.4), reclaim (2.2), paving (2.1) and project patches (2.3) never mutate `world` themselves. They call one primitive, so the side effects and invariants exist once:

```js
// edit = { kind:'raise'|'lower'|'dig'|'fill'|'reclaim'|'pave'|'patch',
//          x, z, w=1, h=1,                       // a rect of tiles
//          from:{kind,height,water}, to:{kind,height,water},   // from is checked against the world (stale edits fail)
//          by:'player'|'project'|'system', project?, via? }
applyEdit(ctx, edit, { dryRun=false }) -> { ok, reason?, changed:[{x,z}], bagged:{item:n}, lost:[], moved:{player?:{x,z}} }
```

1. **Guards.** `ctx.guards.check(kind -> 'terraform'|'reclaim'|'dig', edit)` runs for every tile of the rect; any refusal refuses the whole edit (atomic) with a human reason. The guard payload is exactly the `edit` object above (typed in `core/events.js`).
2. **Cleanup of what stood on the tile** (the generalised `clearSpot()`): props whose footprint touches a changed tile, or whose base is no longer flat afterwards (except `stairs` props placed by `canPlace`), return to the bag (`remove {to:'bag'}`); a crop is removed and gives its seed back; forage is removed; `wetSoil` is cleared; fish spots and sprinkler reach are recomputed.
3. **Mutation** of `kind`/`height`/`water` through the world setters, then derived arrays (`wet`, `stairs`, `flow`, `fall`) are refreshed.
4. **Emit** `terraform {x,z,from,to,kind}` per tile (batched per rect) and `waterChange {rect}` when `water` changed, then `invalidate('terrain')`, `invalidate('veg')`, `invalidate('crops')`.
5. **Player.** A `by:'player'` edit that includes the player's tile is refused ("you are standing there"). A `project` or `system` edit moves the player to the nearest walkable tile reachable from home before mutating.

`dryRun` runs steps 1 and 2 without mutating and reports what would be bagged, so UI previews, the project start check and the completion check all use it.

*As built (S9b).* Guards are asked once per edit, with the edit (defaults filled) as payload, and read the whole rect themselves; `raise`/`lower`/`pave`/`patch` ask the `terraform` guards, `dig`/`fill` the `dig` guards, `reclaim` the `reclaim` guards. A system that calls `applyEdit(ctx, ...)` lists `EDIT_NEEDS` (`props`, `player`, `farming`, `daily`) in its `needs`; `core` itself works too. The cleanup is exported as `clearTiles(ctx, tiles, { dryRun, soilToGrass })` (the shrine's `clearSpot` is a call to it); fixed props (the stall, landmarks) are never bagged. `world.registerDerived(fn)` / `world.refresh(rect)` are the hooks for `flow` and `fall`. Reachability and the soft-lock rules compare the village after the edit with the village before it, so a village that is already cut in two does not freeze every edit; `ctx.use('terrainrules').addAnchors(fn)` adds what must stay reachable (a villager's door).

**Shared invariants (`systems/terrainrules.js`, registered as guards for all three edit kinds, specified and covered by a logic test in S9, extended by 1.2).**
- No edit under a `LANDMARKS` footprint (shrine, stone, pier) or under a bridge or pier deck; no `fill` of the water a deck spans; no edit that cuts a placed road or bridge approach (checked by reachability below).
- **Reachability.** After the edit, the stall, the shrine, the home tile and every placed door tile must stay mutually reachable with `findPath(..., step)` (one flood fill, at most 4096 tiles, so cheap). A dig or raise that would cut the village in two is refused with "that would cut the path to the shrine".
- **Soft-lock safety.** Nothing is missable forever (`docs/DESIGN.md` rule 1): an edit may never remove the last reachable fresh-water fishing tile, the last reachable sea-shore tile or the last tillable soil tile.
- **Load-time `ensurePlayerWalkable`** (`systems/player.js` `start`, after catch-up): if the saved player tile is not walkable or not reachable from home, the player is placed at the nearest tile that is, else at home. This also covers a patch applied during catch-up and a v3 to v4 re-centring.

**Project patches over player content (2.3, applied through `applyEdit({by:'project', kind:'patch'})`).** Props on a patched tile go back to the bag and the away summary gets a line ("Your lantern was put back in the bag"); crops return their seed; the patch never overwrites the saved player tile (rule 5). A project cannot complete over a tile that violates a guard: at completion `dryRun` is run, and a violation (for example a guard added by a later WP, or a reachability rule that the player's own later edits now violate) moves the project to a `waiting` state with a reveal-card line saying what to move, with no cost and no timer penalty; it completes the next time `dryRun` passes (checked on resume and when props change). `start` also runs `dryRun` so a project cannot be started when it can never finish.

**Interfaces other modules need.**
- *Render (1.1, 1.4):* per-chunk read of `kind`, `height`, `water`; `world.dirty` chunks; no global `WATER_Y`.
- *Picking (1.2):* `raycast(origin, dir) -> {x, z, y}` marches the heightfield and replaces `intersectPlane` in `groundTile`.
- *Pathfinding (1.2):* `findPath(start, goal, walkable, W, H, maxNodes, step?)`. `step(x0,z0,x1,z1)` returns false or a cost; the old positional call stays valid. `maxNodes` becomes 12000 (64x64 = 4096 tiles).
- *Props:* `canPlace` runs the `place` guards (flat footprint unless the prop has `stairs`); mesh y comes from `groundY`; `BillboardLayer` items accept an optional `y`.

**Centring.** `new World({w:64,h:64})` embeds the legacy 40x40 island at offset `LEGACY_OFF = 12` (identical shape, asserted against `legacy40`). `coords.legacy(x,z)` maps authored coordinates (`LANDMARKS`, the `newGame` layout, the player start in `Game` and `main.js`, and every test coordinate via `__game.L(x,z)`); in Wave 0 `LEGACY_OFF` is 0, so `legacy` is the identity. **The conversion of every authored literal happens in S9, while `LEGACY_OFF = 0`**: S9 rewrites each coordinate in `tests/smoke.mjs`, `tests/mobile.mjs`, `tools/shot.mjs`, `Game`, `shrine` and `main.js` (about 110 in the tests) to go through `L()`/`legacy()`, including `tileToScreen`, `pos.set`, `tap({x,z})`, `world.get(x,z)` and field-tile ranges, and S12 extracts the flows from the already-converted files. 1.3's gate for the shift is then only flipping the constant, adding the `wp13-grow64` migration and running the suites, and 1.3 never edits a file it does not own. A logic test `tests/logic/coords.mjs` greps the flows for a bare integer pair in a coordinate call and fails on it. 1.3 registers the `wp13-grow64` env migration: grow the `world` arrays into 64x64 (sea elsewhere), then `shiftAll(env, 12, 12)`. Slices with coordinates declare `shift`: `props`, `farming` (crops and wet soil), `daily` (forage), `core` (player), `scheduler` (`xz` fields).

## 6. Characters

Villagers and visitors are **simple low-poly 3D bodies** painted by the same projection pipeline as props, so each is a blockout.

**Blockout.** An entry with `kind:'character'` in a pack, in a rest pose with limbs slightly apart so the iso render sees them. Each `part` has `bone:'armL'` etc. `assets/blockouts/geometry.js` builds a merged geometry plus `skinIndex`/`skinWeight` (weight 1 per vertex, one bone per part), returned as a `SkinnedMesh` with named bones. **That skinned variant is S13's (orchestrator-owned); 3.1 and 3.2 only consume it.** The pipeline renders it unskinned, like any prop (`jobs.mjs` iterates `Object.keys(BLOCKOUTS)`).

**Painting.** `makePaintedMaterial` is unchanged for skinned meshes (see the facts at the top). The projection samples the bind pose, so paint follows the limbs. Two gaps: the material uses 2 azimuths, so side-on views are covered only at grazing angles; and nothing proves 2 is enough for faces. S13 adds a per-blockout `azimuths` field (default `[45, 225]`), `jobs.mjs` reads it, and `makePaintedMaterial` builds N <= 4 samplers; `makePaintedMaterial` hard-codes `uPaint0/1` today, so the cache key changes from `'painted-projection-v2'` to `'painted-projection-v3'` and includes N. **The 2-vs-4 decision is not a WP task.** Painting is a Codex run, and `assets/painted/**` and `pipeline/out/**` are orchestrator-only, so it cannot happen in a fork. Gate **G2** (orchestrator, after S13, before any Wave 3 fork starts; it may run during Wave 2) builds one prototype biped and one quad blockout, runs them at 2 and at 4 azimuths, compares portrait screenshots at game zoom, and writes the result to `docs/CHARACTERS.md` (`azimuths: [..]` per rig, the painted-asset naming, the budget check). 3.1 and 3.2 read that file at fork time and set `azimuths` on their blockouts accordingly. Fallbacks: the vertex-colour Lambert shows until art exists, and billboards (`vegetation.js`) if projection fails; `characters.spawn` hides the choice.

| rig | bones |
|---|---|
| `biped` | root, torso, head, armL, armR, legL, legR (+ hand for tools) |
| `quad` | root, torso, head, tail, legFL, legFR, legBL, legBR (tanuki, fox, deer) |
| `bird` | root, torso, head, wingL, wingR (crane) |

Budget: at most 1,200 triangles and 12 bones per body, one draw call each, at most 14 characters in view.

**Animation.** `animator.js` plus per-rig clips in `rigs/<rig>.js`: `idle, walk, sit, sweep, fish, wave, sleep, carry`, as pure functions of `(rig, t, params)`.

**Interface** (`render/characters/api.js`, frozen in Wave 0):

```js
characters.spawn(def, { x, z }) -> { root, setSpot(x, z, rot), play(clip, opts), dispose() }
```

If `painted.assets[def.body.blockout]` is missing, `spawn` returns the procedural body from `render/character.js` `buildCharacter(def.look)` with `animateCharacter` as its clip set; this is also the player and Hana until painted. `render/character.js` stays untouched otherwise (parts `body, head, armL, armR, legL, legR, hand`).

**Data** (`add('villagers', ...)` in `packs/wp31-villagers.js`):

```js
add('villagers', 'ume', { name: 'Ume', title: 'Tea master',
  body: { blockout: 'char_ume', rig: 'biped', height: 1.0 }, look: { robe, sash, hair, hat },
  home: { project: 'ume_house', door: { x, z } }, wish: { near: { prop: 'tea', r: 3 }, terrain: 'grass' },
  likes: { items: ['tea'], tags: ['flower'] }, dislikes: { items: ['fugu'] },
  schedule: [ { hours: [6, 9], at: 'home.door', do: 'sweep' }, { hours: [9, 12], at: { near: { prop: 'tea' } }, do: 'idle', when: { weather: '!rain' } },
              { hours: [19, 24], at: 'home', do: 'sleep' } ],
  hearts: [{ n: 2, unlock: { recipe: 'matcha' } }], dialogue: [{ id, when: cond, once, lines: [] }] });
```

The schedule is a **pure function** `spot(def, ctx, ms)` with a day-seeded rng, so nothing is simulated while away. The view walks the mesh to the target with `findPath`, and snaps if more than 6 tiles behind. Visitors use the same shape plus `arrive: cond`, `stayMs`, `gifts`, `hint`. An hourly `visitorRoll` scheduler entry draws from `rng(dayKey, visitorId, hour)` so catch-up is reproducible; `visit {phase:'arrive'}` with `away:true` feeds the summary.

**Mail (3.1, `systems/mail.js`).** Hana's daily letter and later villager letters share one inbox. Slice `mail` (order 71): `{ inbox:[{id, from, at, read, lines, gifts}], seq }`. Delivery is a `sched` entry of kind `wp31.mail` (`catchUp:'each'`, so letters that arrived while away all appear, capped at 30 kept), whose handler adds to the inbox, emits `mail {from,id}` and feeds the away summary ("3 new letters"). A daily `mail` contributor (`ctx.daily.contribute`, own sub-stream) picks Hana's letter from `P/wp31-villagers.js` text blocks; gifts attach to the letter and are taken when it is opened, so nothing is lost if the player never opens it. The `mailbox` sheet (`U/mailbox.js`) is registered in `ui/sheets/index.js` as a stub in S12, and the mailbox prop opens it. If 3.1 slips, Wave 3 ships without letters and the stub stays empty; nothing else depends on it.

**Risks and mitigations.**
- **S6 regressions.** Verbatim first, then rewrite; goldens and both browser suites after every group; S6A and S10 are never parallelised.
- **Event order.** `requestsDone` moving to an event changes toast and refresh order: pin with `PRIO` bands and a smoke assertion. Coalesce `itemGain` refreshes to once per frame.
- **Hidden coupling.** `Daylight` reads `game.props.version`, `game.veg`, `game.cropLayer`, `game.particles`; `input.js` reads `p.mesh.scale`; tests read `__game.game.*`. Keep these as facade properties. `player` stays [T] (`THREE.Vector3`).
- **Daily roll depends on props.** The golden uses a stub props; the browser suite covers real layouts.
- **Save loss.** `pre-v4` backup, fixtures, idempotence, unknown-slice preservation; restore a real v3 `RCV2` code before S10 merges. A failed load never reaches `newGame()` or a write (section 3.7), and the quarantine copy is the last resort.
- **Module count (about 200 requests cold).** Flat indices, lazy sheets, preload tags, a budget test; measure on a real phone in S13.
- **Stale or mixed modules.** Network-first with a 4 s race can serve an old module beside new ones. Defences, all of which exist from S10: `BUILD_ID` mismatch shows the update card and goes read-only; a save with a newer `v` is never written; the cache name changes with `BUILD_ID`, which the orchestrator regenerates at the end of every wave. Browser flows other than `offline` load with the existing `?nosw` param.
- **Over-abstraction.** Registries only where a central switch exists today; conditions grow through `cond.define`.
- **Characters are the unknown.** The procedural body and billboards stay behind `characters.spawn`; the azimuth decision is an orchestrator gate (G2), not a WP task.
- **Fork isolation.** Each WP must pass `npm run test:logic` in its own copy: real schemas and shared ids exist from S4, `validateAll` has a `fork` mode, the golden uses a base-only instance, and allocation is checked per fork. If a WP still needs another WP's output, the matrix is wrong and the orchestrator fixes the matrix before the wave starts.
- **Tile edits.** One primitive (`applyEdit`) owns cleanup, invariants and reachability; a direct world mutation elsewhere fails `arch.mjs`.
